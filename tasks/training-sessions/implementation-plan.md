# training-sessions: Implementation Plan

Sources: `tasks/training-sessions/requirements.md`, `frontend-accelerator-onboarding/TASK.md`, and the user's decisions on the open questions.
Application root: `/home/user/my-app` (React 19 + TypeScript, Vite, npm with `package-lock.json`, ESLint flat config).
Status: plan only. No production code, config, or dependency has been changed.

## 1. Decisions (resolved open questions)

| # | Question | Decision |
|---|----------|----------|
| 1 | Mock mechanism | MSW (`msw`), a conventional HTTP mock. Browser worker for `npm run dev`, node server for tests. Both share one handler set. |
| 2 | Test tooling | Vitest + jsdom + React Testing Library (`@testing-library/react`, `/user-event`, `/jest-dom`). Vitest reuses the existing Vite config and is the standard pairing for Vite. |
| 3 | Statuses | `scheduled`, `completed`, `cancelled`. A new session is created as `scheduled`. |
| 4 | List error recovery | Error message plus a "Retry" button that refetches. |
| 5 | Created session vs. active filter | If the new session does not match the active filter, reset the filter to `All` so it is visible. If it matches, keep the filter. Since new sessions are always `scheduled`, this means: filter `scheduled` or `All` keeps the filter, while `completed` or `cancelled` switches to `All`. |
| 6 | Empty state | Text "No sessions yet". Shown when the visible list is empty. |
| 7 | Date/time | `<input type="datetime-local">` (local timezone). Display uses the browser locale and time zone via `Intl.DateTimeFormat(undefined, { dateStyle: 'medium', timeStyle: 'short' })`. |
| 8 | Create-request failure | One understandable, recoverable error inside the modal. The modal stays open, the input is kept, and the user can press submit again. |
| 9 | Form presentation | Modal dialog. |

Implementation notes on the decisions:

- Decision 6: the filtered-empty case also shows "No sessions yet". Keep one message and do not add extra copy.
- Decision 9: use a `div` with `role="dialog"`, `aria-modal="true"`, and `aria-labelledby`. Do not use native `<dialog>.showModal()`, because jsdom support is unreliable. Add Escape-to-close, a Cancel button, and focus on the title input when the dialog opens.
- Persisting sessions across page reloads is out of scope. The mock store lives in memory inside the handlers module.

Why each file:

- `types.ts`: shared `SessionStatus`, `TrainingSession`, `CreateSessionInput`. This is the contract between the API, the hook, and the UI.
- `validation.ts`: pure, UI-free rules for the title and the date. They are unit-testable with an injected `now`.
- `format.ts`: the date formatting helper and the status labels. It keeps locale logic out of components.
- `api.ts`: the replaceable request boundary. It is the only place that calls `fetch`. Components never import MSW or mock data.
- `useTrainingSessions.ts`: owns list state (load, error, retry, create, filter reset). It keeps the components presentational.
- `SessionFilter.tsx`, `SessionList.tsx`, `CreateSessionModal.tsx`: presentational pieces. The list holds the loading, error, empty, and item states.
- `TrainingSessionsWorkspace.tsx`: the composition root of the feature (header, filter, "Create session" button, list, modal).
- `mocks/*`: MSW handlers, seed data, browser worker, and node server. They sit outside the feature folder so the mock layer is clearly separate and removable.
- `test/setup.ts`: jest-dom matchers, MSW server lifecycle, and cleanup.
- `vite.config.ts`: one added `test` block, with no changes to the existing plugin setup.
- `package.json`: new devDependencies and the `test` script. Existing scripts are unchanged.
- `main.tsx`: starts the MSW worker in dev before the first render.
- `App.tsx` and `App.css`: the Vite starter content is replaced and is not part of the feature.

## 3. Step order and contracts

Each step lists what it needs from earlier steps and what it exposes to later ones.

### Step 1: Tooling and dependencies

Actions:
1. `npm install msw`. Dev-only use is acceptable, so use `npm install -D msw`.
2. `npm install -D vitest jsdom @testing-library/react @testing-library/user-event @testing-library/jest-dom`.
3. `npx msw init public/ --save`. This generates `public/mockServiceWorker.js` and adds `msw.workerDirectory` to `package.json`.
4. Add the script `"test": "vitest run"` to `package.json`. Optionally add `"test:watch": "vitest"`.
5. In `vite.config.ts`, import `defineConfig` from `vitest/config` and add:
   `test: { environment: 'jsdom', globals: false, setupFiles: ['./src/test/setup.ts'], css: false }`.

Exposes: `npm test` runs Vitest. The existing `dev`, `build`, and `lint` scripts keep working.
Check: `npm run build` and `npm run lint` still pass (no test files yet).
Risk: `tsc -b` type-checks `src/**`, so test files and `vitest` types must compile. Use explicit imports (`import { describe, it, expect } from 'vitest'`) and do not edit `tsconfig`. If `tsc -b` complains about `vite.config.ts` types, check `tsconfig.node.json` first.

### Step 2: Types, validation, formatting (pure modules)

Contract in `types.ts`:
```ts
export type SessionStatus = 'scheduled' | 'completed' | 'cancelled'
export type SessionFilterValue = 'all' | SessionStatus
export interface TrainingSession { id: string; title: string; status: SessionStatus; startsAt: string /* ISO 8601 UTC */ }
export interface CreateSessionInput { title: string; startsAt: string /* ISO 8601 UTC */ }
```

Contract in `validation.ts`:
```ts
validateTitle(raw: string): string | null            // null = valid; trims; 3..80 chars
validateStartsAt(raw: string, now?: Date): string | null // raw is the datetime-local value; empty = required; must be > now
```
Messages are user-readable, for example "Title must be at least 3 characters", "Title must be at most 80 characters", "Choose a date and time", "Date and time must be in the future".

Contract in `format.ts`: `formatStartsAt(iso: string): string` (browser locale and time zone) and `STATUS_LABELS: Record<SessionStatus, string>`.

Conversion rule: the form converts the `datetime-local` string (local time, no zone) to ISO with `new Date(value).toISOString()` before calling the API. The API only deals in ISO strings.

### Step 3: Request boundary (`api.ts`)

Contract:
```ts
listSessions(signal?: AbortSignal): Promise<TrainingSession[]>   // GET  /api/sessions
createSession(input: CreateSessionInput): Promise<TrainingSession> // POST /api/sessions
```
- Both throw an `Error` with a readable message on a network failure or a non-2xx response. They do not return partial data.
- The URL is built with `new URL('/api/sessions', window.location.origin)` so that `fetch` works under jsdom and Node (relative URLs are not valid there).
- Nothing outside `api.ts` calls `fetch`. Swapping in a real backend means changing only this file or the base URL.

### Step 4: Mock layer (MSW)

- `mocks/data.ts`: 4 to 5 seed sessions covering all three statuses, with fixed ISO dates.
- `mocks/handlers.ts`: `GET /api/sessions` returns the in-memory list. `POST /api/sessions` returns 201 with `{ id, title: title.trim(), status: 'scheduled', startsAt }` and appends it to the store. It returns 400 on an invalid body, as a mock-layer safety net. Export `handlers` and a `resetSessions()` helper that restores the seed.
- `mocks/browser.ts`: `setupWorker(...handlers)`.
- `mocks/server.ts`: `setupServer(...handlers)`.
- `main.tsx`: if `import.meta.env.DEV`, `await worker.start({ onUnhandledRequest: 'bypass' })` (dynamic import) before `createRoot(...).render(...)`. Production builds do not include the mock.

Contract: handlers implement exactly the shapes from Step 3. Tests override them per test with `server.use(...)` to simulate failures.
Behavior note: add a small artificial delay (about 300 ms) in the browser handlers only, so the loading state is visible during the manual check. Do not apply the delay in tests (use `delay()` guarded by the environment, or define it in `browser.ts` wrappers).

### Step 5: State hook (`useTrainingSessions.ts`)

Contract:
```ts
{
  sessions: TrainingSession[]            // all loaded sessions
  visibleSessions: TrainingSession[]     // filtered
  filter: SessionFilterValue
  setFilter(v: SessionFilterValue): void
  loadStatus: 'loading' | 'success' | 'error'
  retry(): void                          // refetch, sets loadStatus back to 'loading'
  create(input: CreateSessionInput): Promise<void>  // rejects on failure, resolves on success
}
```
Rules:
- Loads on mount. Aborts or ignores stale responses on unmount (StrictMode double-invoke safe).
- On `create` success: append the session to `sessions`. If the new session's status does not match the active filter, set the filter to `all` (decision 5).
- `create` does not touch `loadStatus`. A create failure is handled by the modal, not the list.
- No refetch after create (assumption in the requirements: the list is held in client state).

### Step 6: UI components

- `SessionFilter`: the options are `All`, `Scheduled`, `Completed`, `Cancelled`. Use radios (or buttons with `aria-pressed`) and expose a group label "Filter by status". One value is active at a time.
- `SessionList`: takes `loadStatus`, `sessions`, `onRetry`.
  - loading: text "Loading sessions..." (`role="status"`).
  - error: `role="alert"` with "Could not load sessions. Please try again." and a "Retry" button.
  - empty: "No sessions yet".
  - items: title, status label, and the formatted start date/time.
- `CreateSessionModal`: props `open`, `onClose`, `onSubmit(input): Promise<void>`.
  - Fields: "Title" (text) and "Start date and time" (`datetime-local`, `min` set to now as a hint only; validation is authoritative).
  - On submit: run `validateTitle` and `validateStartsAt`. If either fails, show inline messages tied to the fields (`aria-invalid`, `aria-describedby`) and do not call `onSubmit`.
  - While pending: the submit button is disabled and a `submitting` ref guard ignores a second submit (prevents a double submit even before the re-render).
  - On a failed request: show `role="alert"` "Could not create the session. Please try again." Keep the modal open and keep the values.
  - On success: call `onClose` and reset the form.
  - Escape and "Cancel" close the modal and are disabled while pending.
- `TrainingSessionsWorkspace`: wires the hook, the filter, the list, the "Create session" button, and the modal. The title is an `h1`, "Training sessions".
- `App.tsx`: renders `<TrainingSessionsWorkspace />` only. Remove the starter assets import from `App.tsx`; leave the asset files themselves in place.
- `App.css`: minimal styles (layout, list, modal overlay, error and empty states).

Contract between the hook and the modal: `onSubmit` resolves for success and rejects for failure. The modal alone decides what to display.

## 4. Tests

`src/test/setup.ts`:
- `import '@testing-library/jest-dom/vitest'`.
- `beforeAll(() => server.listen({ onUnhandledRequest: 'error' }))`, `afterEach(() => { server.resetHandlers(); resetSessions(); cleanup() })`, `afterAll(() => server.close())`.

`TrainingSessionsWorkspace.test.tsx` (behavior level, renders the workspace, uses MSW node handlers, queries by role and label):

1. Main flow, load and filter: shows "Loading sessions..." first, then the seed sessions with title, status, and formatted date/time. Choosing "Completed" shows only completed sessions. Choosing "All" shows all of them again.
2. Main flow, create: open the "Create session" dialog, enter a valid title and a future date/time, submit. The dialog closes and the new title appears in the list with the status "Scheduled".
3. Created session and an active filter: with the "Completed" filter active, create a session. The filter returns to "All" and the new session is visible. With the "Scheduled" filter active, the filter stays "Scheduled" and the session is visible.
4. List error and retry: `server.use` makes GET return 500. The alert is shown. After restoring the handler and clicking "Retry", the sessions appear.
5. Empty state: `server.use` returns `[]`, and "No sessions yet" is shown.
6. Create validation: a title with 2 characters, or only spaces, shows a title message. An empty date shows "Choose a date and time". A past date shows the future-date message. No POST is sent (assert with a handler counter).
7. Double-submit prevention: a POST handler is delayed. Clicking submit twice sends exactly one request and the button is disabled while pending.
8. Create failure: POST returns 500. The error alert appears in the modal, the modal stays open, and the entered values are kept. A second submit with a working handler succeeds.

`validation.test.ts` (small unit tests):
- Title: trims whitespace, rejects fewer than 3 or more than 80 characters, accepts 3 and 80.
- Date: empty is rejected, a past value is rejected, a future value passes (inject `now`).

Required minimum from the task: at least one behavior-level test of the main flow. Tests 1 and 2 satisfy it. The others cover the user's decisions (4, 5, 6, 8).

Test hygiene: compute "future" dates relative to the current time inside the test (for example now plus 1 day, formatted as `YYYY-MM-DDTHH:mm` in local time). Use no hardcoded calendar dates for form input. Date display assertions should compare against `formatStartsAt(...)` output, not a hard-coded locale string, so the tests do not depend on the machine's locale.

## 6. Scope guardrails and risks

- No backend service. No routing, search, pagination, details view, or persistence.
- No changes to unrelated config. The only config edits are the Vitest `test` block in `vite.config.ts` and the `package.json` additions.
- The `msw` and `vitest` major versions are resolved by npm at install time. If the install resolves a version with a peer-dependency conflict against Vite 8, report it and do not force it (no `--force` or `--legacy-peer-deps` without confirmation).
- `public/mockServiceWorker.js` is a generated file and is expected to appear in the diff. Do not edit it by hand.
- `msw init` and `npm install` change the filesystem and the network use, so confirm with the user before running them during implementation.
- Date/time tests depend on the system clock, so keep them relative to now.
- Before implementing, check the new files against the ESLint `react-refresh` rule: component files should only export components. The hook, the helpers, and the types are kept in separate files for that reason.
